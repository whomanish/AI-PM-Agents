# Support FAQ

Use this guide to help support readers distinguish:

- Expected behavior.
- Access or configuration questions.
- Known limitations.
- Suspected or confirmed defects.
- Unknown behavior requiring investigation.

Classify an issue only when the supplied evidence supports that classification. Give steps, settings, commands, workarounds, escalation destinations, and fix timing only when verified for this case. Technical plausibility is not evidence. Do not manufacture a fix date, workaround, contact, channel, or future resolution. Label any inferred investigation follow-up as a proposal or open question, never a confirmed assignment; a missing owner does not mean unassigned.

When the answer is unknown, say so plainly and identify what remains to be established. Use an escalation path only if one is supplied. Distinguish confirmed facts from questions for investigation, and do not describe “no known issues,” “no workaround,” “not assessed,” or “not defined” unless that exact state is explicitly confirmed. Missing information should be marked as not supplied or not confirmed, not as an organizational or product state.
